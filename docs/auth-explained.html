How login and permissions work

A walkthrough of authentication ("who are you?") and authorization ("what are you allowed to do?") in the AgentBridge Booking demo — written to work for a non-technical reader, a new hire, and a developer picking up the code for the first time. Skim the plain-language parts; the small dashed code like this boxes point at the exact file if you want to go deeper.

1The 30-second version

Think of the app as a hotel, and think about what happens when you walk in.

🪪

Logging in = getting a key card

The front desk checks who you are once, then hands you a key card. You show the card, not your ID, every time you open a door after that.

🍪

The session cookie is that key card

Your browser holds a small signed cookie. It proves who you are for up to 7 days without you logging in again.

🗝️

Your role decides which doors open

A guest's card opens the room. A manager's card opens the office and the safe. Same idea here: customer, support, or admin.

🤖

An AI agent gets its own, shorter-lived card

An assistant acting on your behalf carries a separate card that expires in 8 hours, not 7 days — a shorter leash for something automated.

🛑

Risky actions get an "are you sure?"

Canceling a reservation, refunding a payment, checking someone out, deleting a task — these always pause for confirmation before they happen.

2Glossary

Plain-English definitions for the words used throughout this page.

Authentication
Proving who you are. ("You are alice.")
Authorization
Deciding what you're allowed to do, now that we know who you are. ("Alice may book a table, but not issue a refund.")
Session
The period during which the app remembers you're logged in.
Cookie
A small piece of text the browser stores and automatically sends back on every request — here, it's the proof-of-login for a person using the website.
Token
Like a cookie, but designed to be copy-pasted and handed to a separate program (an AI agent) instead of living quietly in a browser.
Role
A label — customer, support, or admin — that determines which actions are allowed.
HMAC signature
A tamper-proof stamp glued to a cookie or token. Anyone can read it, but only the server (which holds the secret key) can produce a valid stamp — so a forged or edited one is instantly detected.
MCP
Model Context Protocol — the standard an external AI agent uses to call this app's tools over the network.
WebMCP
The same idea, but for an agent running inside the web page itself, alongside a human using the same browser tab.

Figure: token/cookie anatomy. Anyone can read the payload — it isn't encrypted, just signed. But nobody without the server's secret key can produce a matching signature, so editing the payload (say, changing role from customer to admin) instantly breaks the signature and the server rejects it.

Nothing is stored on the server to check against — no database table of "active sessions." The signature is the proof. That's a deliberate choice for this app: it runs on Vercel, where each request can land on a different server instance with no shared memory, so there's nothing durable to look a session up in anyway.

5Life of a login

What happens to your session from the moment you arrive to the moment it's gone.

Created

On sign-in or role switch. If you show up with no valid cookie, you're sent to the login page (or, with DEMO_MODE=true, signed in as alice automatically).

Validated

Every request re-checks the signature, the role, and the expiry — there's no "remembered" state to trust instead.

Expires

7 days for the cookie, 8 hours for an agent token. After that it's just rejected, like any other invalid signature.

Logout

Clears the cookie from your browser. There's nothing server-side left to clean up.

codeapp/page.tsx (login gate) · getOrProvisionUser in lib/auth-tokens.ts · app/api/logout/route.ts (logout)

Signing in is required by default. Two conveniences exist because this is a demo: a "switch role" button lets a signed-in user jump straight to support or admin with no password, so one login can see every role; and with DEMO_MODE=true an unauthenticated visitor is auto-signed-in as alice/customer instead of seeing the login page. DEMO_MODE=false keeps login required and also turns the role switcher off.

6Three doors into the system

A booking action — say, "cancel this reservation" — can be triggered three different ways. All three end up running the exact same code and the exact same permission check; only the front door is different.

A person clicks a button

  1. Browser sends the request with its session cookie
  2. POST /api/call reads the cookie, identifies you
  3. Role check → input validation → the action runs
  4. Result is written to the audit log

An in-page AI helper

  1. Agent code running in the same browser tab calls a registered tool
  2. It re-uses your session cookie — it has no credential of its own
  3. Goes through the same /api/call as the button above
  4. Same role check, same audit log

An external AI agent

  1. Calls POST /api/mcp with an Authorization: Bearer token
  2. The token is verified and turned into a user + role
  3. Tool list is filtered to that role; the call is re-checked again
  4. Same audit log

Figure: three entry points, one shared set of rules. The role check happens at least twice on the MCP path — once to decide which tools an agent even sees, once again when it actually calls one — so an agent can't reach a tool it merely knows the name of.

Two more layers on top of the role check

Ownership. A role check alone would let any customer see any other customer's reservation. So on top of the role gate, several operations also check "does this record actually belong to you?" — a customer can only see, cancel, or pay for their own reservations and complete their own tasks.

8Planned: custom roles, per-user permissions & field restrictions

🚧 Planned — design under review, nothing on this page below is built yet

Today the three roles above are fixed in the code, and there's no screen for adding a user or trimming what one specific person can do. This section previews a design for an admin-only Access page that would let you manage that yourself — written up here so it can be reviewed before anyone builds it.

The shift in thinking

Right now, "can this person do X?" is answered with one question: is their role ranked high enough? The plan changes that to two questions, checked live on every request instead of decided once at login: does this specific person hold the permission for X, and are they allowed to send these particular fields?

🧩

A role becomes a starting kit

Roles still exist and still save time — but they're now a bundle of permissions you assign, not a hard ceiling.

➖

One person can lose one permission

Give a specific support user every support permission except checking guests out — without inventing a whole new role for them.

🔒

Even a single field can be locked

Let someone update a guest's name and phone number, but not their email — on the very same action.

⚡

Changes apply immediately

No re-login needed. A permission change on the Access page takes effect on that person's very next click.

New vocabulary

Permission
The right to call one specific action (e.g. checkOutGuest), or to manage access itself.
Role definition
A named, editable bundle of permissions — the three existing roles become the starting set, no longer fixed in code.
Grant
A permission added to one person on top of their role.
Deny
A permission removed from one person, even though their role would normally include it. Deny always wins over both the role and a grant.
Field restriction
A specific input (like email on "update guest") that a role or person isn't allowed to send, even though they can call the action itself.

Worked example

Suppose an admin adds a new employee, dana, starting from the support role — but dana shouldn't be able to check guests out, and shouldn't be able to change a guest's email address even though she can update their name and phone.

The result: dana can do everything support normally can, except check-out — that button simply won't appear for her, and the server rejects it if forced. She can still call "update guest," but sending an email value comes back as rejected, whether the call comes from her clicking a button, an AI helper acting on her behalf in the same browser tab, or an external agent calling in with her credentials — because all three would go through the same central check.

The Access page (sketch)

  • Users tab: add a person, assign their role, and adjust their individual grants/denies and field restrictions, with a live preview of what they end up able to do.
  • Roles tab: edit what a role includes by default, or create a new role from scratch or by copying an existing one.
  • Two safety rails built in: the admin role can never lose the ability to manage access, and the very last person who can manage access can't be deleted or locked out — so nobody can accidentally strand the whole system with no admin.

What stays the same

The demo conveniences described earlier — optional auto sign-in (DEMO_MODE=true) and the one-click role switcher — are planned to keep working the same way, still switched off by DEMO_MODE=false. And access management itself is planned to be something only a person can do through the Access page — never something an AI agent can call as a tool, so an agent can never grant itself more access.

For the authorization decision itself — a flowchart and code comparison of exactly how the permission check changes, plus a worked request-by-request trace — see authorization-design.html. A full technical design (data storage, exact files, API routes, and tests) exists as a separate implementation plan for whoever builds this, once the design above is approved.

9For developers: adding a new operation safely

Every operation lives in lib/operations/ and follows the same shape. When you add one, work through this list:

  • Set roles: [...] to the minimum role that should be allowed to call it.
  • Set requiresConfirmation: true if the action is destructive or hard to undo.
  • Declare outputSchema (the shape of the success data) and add a case to tests/unit/output-contract.test.ts. Input is validated strictly, so build fields from the helpers in lib/operations/schemas.ts.
  • If the data belongs to a specific user, check ctx.userId inside the handler — the role check alone doesn't do this for you.
  • If you're adding a new API route (not a new operation), call getOrProvisionUser() yourself and return 401 when it gives no user — middleware.ts deliberately does nothing (Edge can't verify signatures), so each route is responsible for its own auth check.
  • Add a case for the new operation to tests/integration/rbac.test.ts so the role gate is covered by an automated test.

10FAQ

Why was I logged in automatically, without a login screen?

That only happens when the deployment sets DEMO_MODE=true, which lands a first-time visitor on the URL already signed in as alice (a customer). By default the app sends you to the login page first.

Why can't the AI agent see the admin tools?

Whatever role the agent's token carries, that's what it's limited to — the tool list an agent even sees is filtered down to its role before it can call anything, and the call itself is checked again regardless.

What happens when my token or session expires?

The next request with it simply gets rejected, the same way a request with a tampered or invalid signature would. A browser session gets a fresh 7-day one on next login; an agent token is reissued the next time the page calls /api/me.

Is the custom roles / per-user permissions feature live yet?

No — section 8 is a design preview for review and approval. Nothing on this page describes code that exists today; the rest of this document describes the app as it actually works right now.

Is my password stored anywhere I should worry about?

The three demo accounts use plaintext passwords on purpose — this is in-memory demo data, not a real user database. It's not a pattern to copy into production code.
