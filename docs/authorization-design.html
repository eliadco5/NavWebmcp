Authorization: today vs. planned

A focused look at just the authorization decision — the moment the server decides "can this specific request go through?" — comparing exactly how that works right now with how it's planned to work once custom roles and per-user permissions exist. For the wider picture (authentication, sessions, tokens), see auth-explained.html.

🚧 The "Planned" half of this page is a design for review — nothing described there is built yet

1How it works today Today

Every action ("cancel a reservation," "issue a refund"...) is code that declares a fixed list of roles allowed to call it. The check is one question: is the caller's role ranked high enough?

Request arrivesUI click, in-page agent, or external MCP agent
↓
Read the caller's roledecoded straight from the signed cookie/token — no lookup
↓
Is role's rank ≥ the operation's minimum role?roleSatisfies(role, op.roles)
↓
YES
Run the handler
NO
403 FORBIDDEN

Figure: today's authorization decision. It's a single yes/no gate, and it's the same shape at all three entry points — the UI's /api/call, the in-page agent's bridge, and the external MCP adapter each run this same check independently, using the same shared function.

This works, but it means: three fixed roles, no per-user exceptions, and no field-level control — a support user either can or can't call updateGuest at all; there's no way to let them change a name but not an email.

The single yes/no gate becomes two questions, both resolved fresh on every request by looking up a stored policy — never decided once at login and carried around in a token.

4Where the check lives (unchanged set of places)

The plan doesn't add new checkpoints or remove any — it swaps what runs inside the same checkpoints that exist today.

  • app/api/call/route.ts — the browser / in-page-agent path
  • lib/adapters/mcp.ts — the external MCP agent path (twice: filtering the tool list, and re-checking on call)
  • lib/operations/dispatch.ts — the invoke / composite-operation path
  • lib/operations/loadTools.ts, describeTool.ts — tool discovery
  • lib/capabilities.ts, lib/modules.ts — capability & module listings
  • lib/agentbridge.ts — in-page tool registration and calls

Every one of these currently imports roleSatisfies from lib/auth.ts. The plan is to swap that single import for can / authorize from the new lib/access/policy.ts — one file, same call sites.

5Worked example: three requests from dana

Dana is set up with the support role, a deny on checkOutGuest, and a field restriction on updateGuest's email field. Here's what happens on three different calls she might make.

1. Dana calls checkOutGuest

Input: { reservationId: "res_42", confirm: true }
↓
can(dana, "checkOutGuest")? → support role normally includes it, but dana has a personal deny
↓
403 FORBIDDEN deny wins

2. Dana calls updateGuest including an email change

Input: { guestId: "g_001", name: "Dana R.", email: "new@x.com" }
↓
can(dana, "updateGuest")? → yes, support role includes it pass
↓
Is "email" restricted for dana on updateGuest, and present in the input? → yes
↓
403 FORBIDDEN_FIELD field-level

3. Dana calls updateGuest without touching email

Input: { guestId: "g_001", name: "Dana R." }
↓
can(dana, "updateGuest")? → yes pass
↓
"email" not present in input → field check passes
↓
Handler runs — name is updated

All three traces run identically whether dana clicked a button, an in-page AI helper acted for her, or an external agent called in with her token — the decision is made once, centrally, not re-implemented per entry point.

Why check the field on the raw input, not after validation?

Zod (the validation library already used for every operation's input) silently drops keys that aren't part of an operation's declared schema. If the field check ran after validation, a restricted field could theoretically be smuggled in under a different shape and never get flagged. Checking the untouched raw input first avoids that.
