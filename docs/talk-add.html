The Problem

Current development isn't built for AI

Every team bolting an agent onto their product hits the same wall.

  • Hallucinated calls — guesses at a sequence nothing tells it
  • Non-deterministic — same request, different path each time
  • Endless back-and-forth — a dozen turns to gather one form's worth of input
  • Doesn't connect at all — weeks of bespoke glue just to start
That's not an agent problem. It's an architecture problem: most software was never designed to be consumed — only to be clicked.
The False Fix

Stop Bending Your Platform to Fit an Agent

Why "just add an MCP server" doesn't fix it?

Most integrations wrap a human-shaped API in tool definitions — one tool per endpoint. The agent still has to:

  • Orchestrate multiple calls — the wrapper gave it a schema, not less work
  • Re-read growing context — every call's result reprocessed on the next
  • Learn your domain from the prompt — sequencing, preconditions, dependencies
Wrapping the API is not the same as re-architecting it. MCP is a transport. It was never the fix.
ADD, Defined

You already wrote the business logic.
You just wrote it in the wrong place.

Validation, orchestration, business rules — scattered across every onClick, every useEffect, every route handler that happens to need them.

ADD's one rule: business logic gets its own layer, separate from the UI that triggers it.

One function. One place. The UI becomes what it should've been all along — a thin caller.

The Protocol

NavWebMcp — MCP as transport, not architecture

If your business logic already lives in its own layer, exposing it to an agent is the easy part.

  • Composite operations — one call replaces three or seven
  • Progressive disclosure — a handful of tools at connect, the rest on demand
  • RBAC & confirmation, enforced once — same checks your UI already respects
  • One registry, two surfaces — nothing re-implemented as "the agent version"
If you did the architecture right, this layer is nearly mechanical to add. That's the point.
The Protocol · Under the Hood

Eight meta-tools. Nothing else to install.

Discovery
  • explore — walk the module tree
  • search — glob for operations
  • describe_tool — get the schema
Execution & session
  • invoke — call any op directly
  • load_tools / unload_tools
  • getContext / getCapabilities — preflight
One registration, all eight tools read it
defineOperation({ name: "book", description: "Book a table in ONE step: find a slot, reserve, validate.", inputSchema: { date, time, partySize, name }, permission: "write", // read | write roles: ["customer", "support", "admin"], // who can call it module: "reservation.booking", // where it lives in the tree handler: (input, ctx) => bookOrchestration(input, ctx) })
A completely standard MCP client — Claude Desktop, Claude Code, MCP Inspector. No custom transport. No fork. No special build.
